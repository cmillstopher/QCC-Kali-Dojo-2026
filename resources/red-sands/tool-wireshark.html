Wireshark & tshark

The Packet Analyst mission hands you a capture and some questions. This is the deeper companion: how to filter down to the packets that matter, follow a conversation end to end, and pull the evidence out.

Two filters, and why people mix them up

This is the single most useful thing to get straight:

Capture filter

Decides what gets recorded, set before you capture. Uses BPF syntax (tcp port 21). You can’t get back what it dropped.

Display filter

Decides what you see in an already-loaded capture. Uses Wireshark syntax (ftp, ip.addr==…). Change it as often as you like, nothing is lost.

For the mission you’re handed a finished .pcapng, so you live almost entirely in display filters, the big bar at the top of the window.

Display-filter cookbook

FilterShows
ip.addr == 10.50.70.52Any packet to or from that host. ip.src / ip.dst for one direction.
tcp.port == 21Traffic on a port (here, FTP control).
ftpJust the FTP command channel, logins, commands, banners.
ftp-dataThe separate channel files actually transfer over.
http / dnsFilter by protocol by name.
frame contains "pass"Any packet whose bytes contain that text, great for finding cleartext secrets.
tcp.flags.syn == 1 && tcp.flags.ack == 0Connection starts, a quick way to see who initiated what.
ftp.request.command == "USER"Field-level filtering, pick the exact command or header you want.

Combine with && (and), || (or), ! (not). Wireshark turns the bar green when the syntax is valid.

Follow the conversation

Right-click any packet → Follow → TCP Stream (or HTTP/UDP). Wireshark stitches the whole back-and-forth into one readable window, the entire FTP login, every command, the server’s replies. This is usually where a Packet Analyst answer actually falls out.

# In the stream window:
#  - client text is one colour, server another
#  - "Show data as" → ASCII / Hex dump / Raw
#  - "Filter Out This Stream" to remove it and move on

Let Wireshark summarise for you

The Statistics menu answers “who’s here and what are they doing” without scrolling packets:

Statistics → Protocol HierarchyWhat protocols exist in the capture, by volume. Your map of the whole file.
Statistics → ConversationsEvery host-to-host pair and byte counts, answers “how many hosts, talking to what.”
Statistics → EndpointsEvery address seen, with packet/byte totals.
File → Export Objects → FTP-DATA / HTTPCarve transferred files straight out of the capture, recover that image or document.

tshark: the command line, for evidence and scripts

Same engine, no GUI. Perfect for reproducible evidence and for pulling exact values into your notes.

# read a capture and apply a display filter
tshark -r scribes-ledger.pcapng -Y "ftp"

# print just the fields you want, as a table
tshark -r scribes-ledger.pcapng -Y "ftp.request.command==\"USER\" || ftp.request.command==\"PASS\"" \
  -T fields -e ip.src -e ftp.request.command -e ftp.request.arg

# who talked to whom
tshark -r scribes-ledger.pcapng -q -z conv,tcp

# carve a transferred file back out
tshark -r scribes-ledger.pcapng --export-objects ftp-data,./carved/

Pipe any of these to | tee evidence/ftp_creds.txt so the answer and its proof land in your evidence folder.

The AI angle. People are now pointing LLMs at capture files to ask “was anything sent in the clear?” in plain English, a triage layer on top of the filtering you’re learning here, not a replacement for reading the stream. See AI + Kali: what’s possible.
