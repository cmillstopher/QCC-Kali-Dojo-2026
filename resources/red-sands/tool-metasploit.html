The Metasploit Framework

The Chamber missions tell you to search, use, and check. This page is the deeper companion: what Metasploit actually is, how it’s organised, and how to drive it with intent instead of copy-paste.

  1. The Chamber
  2. Metasploit reference

What it is, and when to reach for it

Metasploit is a framework, not a single tool, a large, organised library of exploit, scanning, and post-exploitation code behind one console. It shines once you’ve identified a specific service and version and want a reliable, well-documented way to validate and demonstrate a known weakness. It is not a first step: you still discover and enumerate by hand first. In the Chamber, it’s the Inner and Burial tool, after Nmap has told you what you’re looking at.

The mental model: modules

Everything in Metasploit is a module. Knowing the five types you’ll meet tells you what a module will do before you run it:

Module typeWhat it does
auxiliaryScanners, enumerators, and checks that don’t deliver a payload: login testers, version grabbers, fuzzers. Safe end of the pool.
exploitDelivers a payload by abusing a specific flaw. This is the one that needs a check first and a volunteer for anything risky.
payloadThe code that runs on the target after an exploit lands, e.g. a Meterpreter session or a plain shell.
postRuns through a session you already have, gather info, loot files, pivot.
encoder / nopReshape a payload to get it past filters. Rarely needed in the lab; good to recognise the names.

Two other ideas you’ll lean on: the database (Metasploit remembers hosts, services, and loot per workspace) and the session (an open connection to a target you’ve landed on).

Start it up

sudo msfdb init        # one-time: start the backing database
msfconsole -q          # -q skips the banner
workspace -a redsands  # keep this engagement's data in its own space
db_status              # confirm the database is connected

Already ran Nmap? Import it so Metasploit knows your hosts and services, or scan from inside the console:

db_import nmap_$TARGET.xml      # pull in an -oX scan
db_nmap -sV -sC "$TARGET"       # or run nmap from msf; results auto-saved
hosts                            # review what the database now knows
services                         # ports/products across the workspace

The core loop, mapped to the Chamber

Find the right module

search & info

search type:exploit name:<product>     # narrow by product you enumerated
info <module>                          # read it BEFORE using: targets, rank, refs, options
use <module>                           # select it (tab-completion works)

Prefer modules ranked excellent/great and read the description, the rank tells you how reliable and how likely to crash the service it is.

Set it up

options & targets

show options            # what the module needs
set RHOSTS "$TARGET"     # the target
set RPORT <port>         # if not the default
show targets            # some exploits need the exact OS/version target id
setg RHOSTS "$TARGET"    # setg = set globally, so you don't retype it
Validate: stop here at the Inner Chamber

check

check     # asks "is this target actually vulnerable?" without firing the exploit

Not every module supports check, but when it does, this is how you confirm a finding without risk. Read what it reports and write it up, that alone completes the Inner Chamber.

Exploit: Burial Chamber, with care

run / exploit → session

set PAYLOAD <payload>    # e.g. a meterpreter or generic shell matching the target
run                     # or 'exploit'; a success opens a session
sessions -l             # list sessions
sessions -i 1           # interact with session 1
Only run a module whose check (or docs) you’ve read. Anything that can crash or lock a service is a volunteer-led demo on the shared lab boxes, coordinate first.

Meterpreter, briefly

Meterpreter is a feature-rich payload that gives you a command channel on the target. A handful of commands cover most of the lab:

sysinfoOS, architecture, hostname. Your first screenshot of proof.
getuidWho you are on the target.
pwd / ls / cdMove around the filesystem.
cat <file>Read a file, e.g. recover a flag.
download <file>Pull evidence back to your Kali box.
shellDrop to a native OS shell.
backgroundPark the session (back to msf>) without closing it.

Console survival kit

backLeave the current module.
sessions -KKill all sessions (clean up after yourself).
spool out.logLog the whole console to a file, evidence.
loot / notesReview what the database has gathered.
exit -yQuit msfconsole.

Keep spool running and screenshot key moments, the Chamber grades the write-up, not the shell.

The AI angle. Assistants can now read a service banner and suggest which module to check, or drive Metasploit through an MCP server, but the check-before-run discipline on this page is exactly what keeps a human accountable. See AI + Kali: what’s possible.
