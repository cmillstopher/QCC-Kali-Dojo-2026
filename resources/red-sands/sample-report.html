Fictional example, not a lab machine. “Northwind Logistics” and host 10.10.10.25 are invented, and the Redis issue below is not present on the Chamber targets (10.50.70.52 / .53). Don’t go looking for this in the lab, use it only to model your own report.

Assessment report

Internal Host Review: app01

Target
app01.northwind.internal (10.10.10.25)
Assessor
A. Scribe
Date
14 November 2026
Scope
Single authorized host; internal network only. No denial-of-service, no destructive actions.

Executive summary

An authorized review of app01 found one high-severity issue, an unauthenticated Redis service exposing all cached application data and allowing write access, and one low-severity information-disclosure issue. The high finding should be fixed before this host handles production data; the low finding is housekeeping. No data was altered or removed during testing.

Approach

Discover (port/service scan) → enumerate the exposed services → validate each issue with the least intrusive check that proves it → document. All activity stayed within the single authorized host.

Findings at a glance

IDFindingSeverity
F-1Unauthenticated Redis serviceHigh
F-2Verbose server version disclosureLow

F-1 · High

Unauthenticated Redis service

CWE-306: Missing Authentication for Critical Function · CVSS 3.1: 8.6 (High), AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:L

Observation
A Redis key-value service is listening on 10.10.10.25:6379 and accepts commands with no authentication, from any host that can reach it on the network.
Evidence
# 1 - discovered during the service scan
nmap -p6379 -sV 10.10.10.25
#   6379/tcp open  redis  Redis key-value store 5.0.x

# 2 - validated: the server answers with no credentials
redis-cli -h 10.10.10.25 ping
#   PONG

redis-cli -h 10.10.10.25 INFO server | head -3
#   redis_version:5.0.x
#   ...

# 3 - confirmed write access, then removed the test key (no data changed)
redis-cli -h 10.10.10.25 set redsands_test 1
#   OK
redis-cli -h 10.10.10.25 del redsands_test
#   (integer) 1

Full output saved to ~/evidence/redis_10.10.10.25.log (via script).

Impact
Anyone on the internal network can read every key the service holds, here, cached session and application data, and write or delete keys at will. Beyond data exposure and tampering, an unauthenticated Redis instance is a common stepping-stone to fuller compromise of the host.
Remediation
  • Require authentication (requirepass or, better, Redis ACLs) and rotate any data that may have been exposed.
  • Bind the service to 127.0.0.1 if only local apps use it; otherwise restrict TCP 6379 at the firewall to the specific app hosts.
  • Ensure protected-mode is on and upgrade to a current, supported release.

F-2 · Low

Verbose server version disclosure

CWE-200: Exposure of Sensitive Information · CVSS 3.1: 3.1 (Low)

Observation
The web service on app01 returns a Server header that names the exact software and version.
Evidence
curl -sI http://10.10.10.25/
#   HTTP/1.1 200 OK
#   Server: Acme-HTTPd/4.2.1
#   ...
Impact
On its own this is minor, but it lets an attacker match the exact version to known exploits without any further probing, useful reconnaissance that costs the defender nothing to remove.
Remediation
Suppress or shorten the Server header (e.g., server tokens off / a reverse-proxy rewrite), and keep the software patched so a disclosed version isn’t a vulnerable one.

Why this works as a report

Notice the shape. It’s exactly the four-part structure from your worksheet, just polished:

Observation

What’s there, stated plainly, target, service, port.

Evidence

The exact commands and their output, saved, anyone could reproduce it.

Impact

What it means in the real world, honestly rated, not “critical everything.”

Remediation

A concrete fix the owner can actually act on.

Two more habits worth copying: a severity that matches reality (the Low really is low), and evidence that is non-destructive and reversible, the write test above was removed immediately and noted.
