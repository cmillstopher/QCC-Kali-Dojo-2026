Document It, Then Report It

Finding the vulnerability is half the job. The write-up is what a real assessment is paid for, and it’s the deliverable here too. This is your toolkit for capturing evidence as you work, organising what you find, and turning it into a report.

  1. The Chamber
  2. Document & Report
The golden rule: if it isn’t captured, it didn’t happen. Capture the command and its output the moment you run it. You can’t re-screenshot a shell you’ve already closed or a target that’s been reset. Every tool on this page is marked on Kali: it ships with a default Kali install, so there’s nothing to download, which matters on the offline Dojo network.
Step 1 · Capture as you go

Record everything the first time

Start a capture before you touch the target, and keep one evidence folder per engagement.

mkdir -p ~/red-sands/evidence && cd ~/red-sands/evidence
script -a session-$(date +%H%M).log      # records your whole terminal; 'exit' stops it
scripton KaliLogs every command and its output to a file. Your always-on safety net.
teeon KaliSave one command’s output and see it: nmap … | tee nmap_$TARGET.txt.
xfce4-screenshooteron KaliKali’s default Xfce screenshot tool (also on the PrtSc key), the cleanest way to capture a GUI tool or a browser finding. Save the PNG straight into your evidence folder.
sha256sumon KaliHash a captured file so you can prove it wasn’t changed later: sha256sum evidence/* > hashes.txt.

Before a screenshot or file leaves your hands, strip its metadata so it doesn’t leak your username or device. See Anonymizing Kali.

Step 2 · Organise your findings

Turn raw output into findings

A pile of log files isn’t a finding. As you confirm each issue, write it up in the same four parts, the same shape the sample report uses.

Observation

Target, service, port, timestamp, the command, and the relevant output.

Evidence

The one screenshot or log excerpt that proves it. Reproducible from your notes?

Impact

What an attacker could realistically do with it in a real environment.

Remediation

The patch, upgrade, config change, or control that closes it.

a text editoron Kalinano or vim in the terminal, or Mousepad on the Xfce desktop. Keep one Markdown file per engagement, a heading per finding.
a folder per hoston KaliNo database needed: a directory per target holding its logs, screenshots, and a findings.md keeps everything together and reproducible.
Step 3 · Build the report

Assemble the deliverable

Open the sample report first and match its structure: title, scope, a findings table with severity, then one section per finding.

Write the whole thing as a single Markdown file in your text editor, folding in the observations and evidence you organised in Step 2. The Markdown file is the deliverable: it reads cleanly as plain text, and anyone can open it.

~/red-sands/evidence/report.md     # one file: scope, a findings table, a section per finding

Need a PDF to hand in? Open the file in Kali’s default Firefox and use Print → Save to PDF, or hand your Markdown to a volunteer at the reporting station. Nothing to install either way.

A good report lets someone who wasn’t there reproduce each finding from your words and evidence alone. Severity, impact, and a clear fix matter as much as the exploit.

Everything here ships with Kali

Every tool on this page, script, tee, sha256sum, the Xfce screenshot tool, a text editor, and Firefox, is already on a default Kali install. On the offline Dojo network that’s the whole point: you can document from the very first command without downloading anything.
