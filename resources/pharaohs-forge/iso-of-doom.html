Station 01 · Concept deep-dive

The ISO of Doom, Explained

The headline activity of the Pharaoh's Forge is building an "ISO of Doom", a custom Kali Linux image that comes out of the oven already set up the way you want it. No experience needed: this page explains what it is, why it's worth building, and how it works, one picture at a time.

  2. ISO of Doom · concept
  3. Boot & test

So what is it, in one sentence?

An ISO of Doom is a single Kali Linux disc image that you've pre-loaded with exactly the tools and settings you want, so every machine you boot from it starts up identical and ready to work, with no manual setup.

An .iso file is just a complete copy of a disc in one file. A normal Kali ISO gives you a plain, stock Kali. A custom ISO, the "ISO of Doom", is one you've baked your own choices into: your mission's tools are already installed, your settings are already applied, maybe even your wallpaper and scripts are already in place.

Where the name comes from. The term was coined by Offensive Security in a 2013 write-up, “Kali Linux ISO of Doom,” describing a custom Kali image that installs itself and quietly phones home for a remote assessment (more on that further down). The hands-on craft of building your own custom ISO was later popularized by the Kali Linux Dojo, the workshops the Kali team ran at Black Hat and DEF CON, where attendees rolled their own image instead of installing a stock one. This station continues that Dojo tradition.

Why bother

Build the recipe once, not every machine by hand

Imagine setting up Kali for a room of ten people. You could install stock Kali on each one and add tools by hand, slow, and no two end up quite the same. Or you write the setup down once as a recipe, build it into an image, and boot that same image everywhere.

Reproducible

The same recipe always produces the same image. No "it worked on mine" surprises.

Fast to deploy

Set it up once. Boot it on ten machines in the time it would take to hand-configure one.

Self-documenting

The recipe is the documentation, anyone can read it and see exactly what's inside.

How it works

A recipe goes into the forge, a bootable image comes out

You don't assemble an ISO by hand. You describe what you want in a folder of config files, and a tool called live-build does the assembly for you, Kali's official way to build custom images.

What's inside the recipe

Four folders, four jobs

The recipe is just a folder tree. You rarely touch most of it, but four spots control almost everything you'd want to change. Here's what each one does, in plain language.

  • Toolspackage-lists/*.list.chroot, the list of software to install. One package name per line.
  • Scriptshooks/, scripts that run during the build to automate tweaks and cleanup.
  • Filesincludes.chroot/, any files you want baked in; they land on the ISO at the same path.
  • Install answerspreseed/*.cfg, pre-answers the installer's prompts for a hands-off (unattended) install.
Where your customizations come from. The aliases, prompt, and setup script you create in Make Kali Yours and the Kali Builder are exactly what goes in hooks/ (to run during the build) or includes.chroot/ (to bake the files straight in). Personalize your environment first, then capture it here.

The build, start to finish

This runs in a disposable Kali/Debian build VM (it needs root, plenty of disk, and time). You won't normally run a full build at the booth. It's slow, but here's the whole shape of it so the pieces above click into place:

# 1 · Get Kali's official recipe
git clone https://gitlab.com/kalilinux/build-scripts/live-build-config.git
cd live-build-config

# 2 · Add your mission's tools to a package list
echo "wireshark" >> kali-config/variant-default/package-lists/kali.list.chroot

# 3 · (optional) Drop files to bake in, under
#      kali-config/common/includes.chroot/...

# 4 · Build it - this is the slow part
sudo ./build.sh --verbose
#   → produces images/kali-linux-*-live-amd64.iso

Steps 2 and 3 are the "recipe" from the diagrams; step 4 is the forge; the .iso it drops in images/ is your ISO of Doom.

One image, two ways to run it

What "Live" means

A beginner's most common question: do my changes stick around? It depends on how you boot the same image.

Live boot

Runs Kali straight off the disc or USB, in the computer's memory, without touching its hard drive. Great for a quick, leave-no-trace session. But anything you change vanishes on reboot, unless you deliberately set up persistence.

Install

The same ISO can install Kali permanently onto a drive, keeping your files and settings between reboots. This is where a preseed file shines: the install can run unattended, start to finish.

Why it earned the name

What people actually build them for

The name traces back to that 2013 OffSec write-up, a real technique for remote vulnerability assessments, not a classroom exercise. Here’s the scenario it described, and the places the same build-once idea shows up across professional security work.

The original scenario

A self-deploying box for a remote internal assessment

The problem. To assess a network from the inside, a tester normally has to travel to the client's site, or ship a machine and then try to reach it. Both are slow and awkward.

The idea. Build a Kali image that installs itself with no questions asked (that's what the preseed file is for), comes preloaded with assessment tools, and on first boot reaches outward to the tester's server over an encrypted VPN tunnel. Firewalls usually permit outbound connections, so the box "phones home" from inside the network. The tester then rides that tunnel back in and works as if plugged into the internal LAN.

The result. The person on-site only has to boot the media, a laptop, a tiny ARM device, whatever's handy. No travel, and the tester gets an authorized foothold on the internal network.

This is a technique for authorized work only. A self-deploying box that calls home is a legitimate professional tool when there's explicit written permission and an agreed scope, and plain malware without it. The authorization is the entire difference. Nothing like this is run at the Arena; here you build a toolkit, not a callback.

The same idea, other jobs

More ways a custom image pays off

Strip away the callback and the core win, "set it up once, boot it identically anywhere", is useful far beyond that one scenario.

Team toolkit image

Every tester on a team boots the same versioned image, identical tools and configs, so findings are consistent and reproducible across the whole engagement.

Drop-box for physical tests

During an authorized red-team or physical engagement, the same callback image on a small ARM device gives an approved internal vantage point past the perimeter.

Internal pivot

After an authorized external foothold, the image can be deployed over PXE or a server's virtual media to turn an external test into an internal one.

Offline / air-gapped kit

Bake in every tool and any offline data so the image works with no internet at all, handy for isolated OT/ICS sites or secure facilities.

Instant lab & CTF reset

Rebuild identical practice environments from one image instead of hand-configuring each, exactly how an event like this one stays consistent across machines.

Incident-response go-kit

A known-good, pre-configured image a responder can boot on scene, with the forensics and triage tooling already in place and verified.

What you'll actually do at the Forge

You don't need to build a full ISO today, a real build is slow. At the station you'll do the part that teaches the idea:

  1. Pick a mission and find the tools it needs.
  2. Open its package list and see how adding a line adds a tool to the recipe.
  3. Watch the facilitator's build demo, or boot the known-good reference ISO.
  4. Verify your tools are present, then carry your mission into the Scribe's Arsenal.
Safety. Only scan and test explicitly authorized Red Sands lab targets, never hotel or conference Wi-Fi. Writing an ISO to a USB erases that drive; use a spare only, and never the 10 attendee loaner USBs.
