Choose your Kali workspace

Your own Kali

Use your installed system or Kali VM. You control the configuration and keep your changes.

  • For a VM, take a snapshot before any system-level change.
  • Use your own account; elevate privileges only when required.
  • Avoid full package upgrades during the event.

Borrow a Live Boot USB

Ten loaner devices are available from volunteers, no personal Kali install required.

  • Return the USB to a volunteer before you leave.
  • Don’t reformat, overwrite, repartition, or install to a loaner.
  • Treat files and settings as temporary unless that device’s persistence is tested and confirmed.
  • Save notes to your own storage or the supplied worksheet.
Persistence isn’t automatic. Live USB persistence has to be set up deliberately. Ask a volunteer about the specific loaner before relying on saved changes.

Step 1

Understand Kali: Linux foundations

A few commands to learn where you are, who you are, and what the system is doing. Don’t memorize, learn to read the results and find help.

Open this guide inside Kali. You’ll type these commands in a Kali terminal, so browse to the Arena site from your Kali instance itself — http://10.50.70.249 on the Kali Dojo Wi-Fi — and keep it open next to your terminal to copy commands and download files as you go.

Navigate & manage files

pwd
ls -lah
cd ~/Documents
mkdir -p ~/red-sands/notes
touch ~/red-sands/notes/session.txt

Users & permissions

whoami
id
ls -l
sudo -l

Notice owner, group, and read/write/execute bits. Don’t change permissions on system files as an experiment.

Processes & system identity

cat /etc/os-release
ps aux
uptime
df -h

Network awareness

ip -br address
ip route
ss -tulpn

These inspect your own interfaces, routes, and listening sockets, not permission to scan others.

For a longer, friendlier intro, see Linux & Kali foundations.

Step 2

Deploy Kali: choose the right form

Virtual machine

Best for snapshots, rollback, isolated labs, and repeatable experiments. Confirm VM networking matches the exercise.

Live USB

Best for a portable try-before-install experience. Persistence depends on how the USB was prepared; the loaners are not to be modified.

Installed system

Best for a dedicated machine. Installation and partitioning are outside this short station, don’t install Kali over a personal system during the event.

ARM devices

Kali supports selected ARM boards; the right image depends on the exact hardware. Treat this as a volunteer-led demo, not a generic image-writing exercise.

Step 3

Configure Kali: inspect, secure, personalize

  1. Review your account and privileges: whoami, id, sudo -l.
  2. Review release and network state: cat /etc/os-release, ip -br address, ip route.
  3. Review listening services with ss -tulpn. Don’t stop services unless you understand the impact and have permission.
  4. Explore kali-tweaks, if available, to learn supported configuration choices.
  5. Personalize: terminal readability, shell prompt, notes folders, and a small mission tool set.
mkdir -p ~/red-sands/{notes,evidence,results,tools}
echo "$SHELL"

Optional shortcut: add alias work='cd ~/red-sands' to your own ~/.bashrc. On a loaner Live USB, treat it as temporary.

Personalize your shell — then capture it. Small tweaks add up fast. Make Kali Yours walks the bash patterns (aliases, prompt, helper functions, a safe setup script); the Kali Builder generates that setup script for you from checkboxes; and terminal multiplexers (tmux) keep long jobs alive and your work organized. Get your environment how you like it here first — it’s exactly what you’ll bake into a custom ISO so every boot starts configured.
Don’t apply blanket hardening. Changing firewall rules, SSH, kernel settings, services, or system-wide controls can break tools and lab connectivity. Ask a volunteer and keep a rollback plan.

Step 4

Build your arsenal: pick a mission profile

These are the same missions you’ll run next door in the Scribe’s Arsenal. Choose one and prepare just its tools.

Packet Analyst

Tools: Wireshark / tshark. Inspect a volunteer-provided capture or approved lab traffic.

tshark --version

Network Mapper

Tool: Nmap. Learn discovery and service identification against the one designated lab target.

nmap --version

Web Analyst

Tools: curl and Burp Suite Community Edition (ships with Kali). Use only the local training app a volunteer identifies.

curl --version

General Purpose

Tools: Nmap, Wireshark/tshark, curl, and a text editor. Learn a few tools well rather than installing everything.

Rules of the Arena

  • Never scan hotel, conference, attendee, or public networks.
  • Only test targets explicitly identified and authorized by a volunteer.
  • Don’t bridge vulnerable lab VMs to hotel Wi-Fi or public networks.
  • Don’t intercept unrelated traffic or collect other attendees’ data.
  • Use synthetic notes only, never real passwords, tokens, client data, or personal information in practice files.
  • Close tools, remove practice artifacts when instructed, and return loaner USBs.
