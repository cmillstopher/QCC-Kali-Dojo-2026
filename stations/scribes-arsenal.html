Mission I · Initiate

The Packet Analyst

Goal: open a capture file and answer four questions about the traffic inside it. No scanning, no network access, just evidence that is already on disk.

Get set up

  1. Open a terminal in your Kali workspace and make a place to work: mkdir -p ~/red-sands/arsenal && cd ~/red-sands/arsenal
  2. Download the capture straight from the Arena site: scribes-ledger.pcapng — or grab it on the command line: wget http://10.50.70.249/assets/pcaps/scribes-ledger.pcapng
  3. Open it in Wireshark (wireshark scribes-ledger.pcapng) or read it on the command line with tshark -r scribes-ledger.pcapng.

Your questions

  1. Which two hosts are talking here, and which one is the FTP server? Give both IP addresses.
  2. What FTP server software and version is running, and where in the capture did it tell you?
  3. The client logs in to the server. What username and password does it send, and why can you read them straight off the capture?
  4. What file does the client download, and how large does the server say it is?
  5. Nothing in this session is encrypted. Besides the login, what else here could anyone on the network capture, and what single change would protect all of it?
Hint: reading the FTP session

Apply the display filter ftp to see just the control channel. The server’s very first reply (the 220 banner) names its software and version; the USER and PASS lines show the login; the RETR line names the file and the server’s 150 reply states its size. On the command line:

tshark -r scribes-ledger.pcapng -Y "ftp" -T fields -e ftp.response.arg -e ftp.request.command -e ftp.request.arg

To read a whole exchange as text, right-click a packet and choose Follow → TCP Stream. To pull the downloaded file back out of the capture, use File → Export Objects → FTP-DATA.

Go deeper → Wireshark & tshark reference.

Done? Take your answers to a volunteer to check against the key. Then push further in the same capture: export the downloaded image out of it, proof that the entire file, not just the password, crossed the wire in the clear.

Mission II · Scribe

The Network Mapper

Goal: run a focused Nmap scan against one lab target and report what you find. This is the only mission that touches a live host, pick one of the two targets below and scan only that address.

Scope, before anything else. Choose one of the two lab targets below and scan that address only. Both live on the isolated lab network (VLAN 70). Do not scan the attendee Wi-Fi, other attendees, the gateway, or any hotel or conference network.
Pick a targetIP addressWhat it is
Linux Metasploitable10.50.70.52An Ubuntu server running web apps, FTP, Samba, a database and more, plenty of surface to map.
Windows Metasploitable10.50.70.53A Windows Server box running SMB, RDP, a web stack and app servers (Jenkins, Tomcat…).

Get set up

  1. Make sure you’re on the Kali Dojo Wi-Fi (the attendee network can reach the lab). Pick one target from the table and set it: TARGET=10.50.70.52 (or 10.50.70.53 for the Windows box)
  2. Check your tool is present: nmap --version
  3. Start with a light service/version scan: 
    nmap -sV -T3 --top-ports 100 "$TARGET"

Your questions

  1. How many TCP ports are open on the target, and which ones?
  2. Pick one open port. What service and version does Nmap report for it?
  3. Add -sC to run Nmap’s default scripts against that one port (for example nmap -sV -sC -p <port> "$TARGET"). What extra detail does it surface?
  4. Which one service here would you look at first in the Hidden Chamber, and why?
Hint: scanning narrowly, not loudly

Narrow the scope with -p to name exact ports (-p 21,22,80) rather than scanning everything. Keep timing at -T3 or lower on a shared lab host so you don’t overwhelm it. -sV asks services to identify themselves; -sC runs safe default scripts; -A does both plus OS detection but is much noisier.

Go deeper → Nmap & NSE reference.

Done? Show a volunteer your port list and your pick for the Chamber. Carry those notes to Station 3. You’ll use them there. Time to spare? Scan the other box and compare how different a Linux and a Windows host look on the wire.

Mission III · High Priest

The Web Analyst

Goal: inspect a training web application by hand with curl, then look at the same requests in Burp Suite Community Edition. Use only the local training URL a volunteer provides.

Get set up

  1. Get the training app’s URL from a volunteer and record it: APP=http://______________
  2. Fetch the page and read the response headers without downloading the body: 
    curl -sI "$APP"
  3. Now fetch the body and follow any redirect, so you see where the app actually sends you: 
    curl -sSL -D - "$APP" -o /tmp/body.html

Your questions

  1. What web server and version do the response headers advertise?
  2. Does the first request redirect? If so, what is the status code and where does it send you?
  3. Find one security-relevant header that is missing (for example Content-Security-Policy, X-Frame-Options, or Strict-Transport-Security). Why does it matter?
  4. Open the same URL through Burp CE’s proxy. Name one thing Burp shows you that the raw curl output did not make obvious.
Hint: curl flags and the Burp proxy

-I fetches headers only; -D - dumps headers to your terminal alongside the body; -L follows redirects; -v shows the full request and response exchange. To send curl through Burp: curl -x http://127.0.0.1:8080 "$APP" with Burp’s proxy listening on 8080. Burp CE ships with Kali. You do not need the Professional edition for this mission.

Go deeper → Burp Suite reference.

Done? Walk a volunteer through your headers and your missing-header finding. That habit, reading what a service tells you before touching it, is exactly what Station 3 rewards.

The discipline behind every mission

Define, select, execute, record

Whatever the mission, the workflow is the same. Tools are easy; disciplined, repeatable work is the skill worth taking home.

1 · Define

State the question you’re answering and name the one authorized target before you run anything.

2 · Select

Choose the smallest set of tools that answers the question. More tools is not more insight.

3 · Execute

Stay inside scope. Keep scans narrow and timing gentle on shared lab hosts.

4 · Record

Capture output, timestamps, and assumptions so another person could reproduce your result.

Mission complete?

Check off what you accomplished. A volunteer can stamp your Arena passport for any mission you finished.

Rules of the Sands

  • Work only against the supplied captures and the single lab target a volunteer authorizes.
  • Never scan or test hotel, conference, attendee, or public networks.
  • Keep scans narrow and timing gentle, the lab targets are shared by everyone.
  • Do not intercept other attendees’ traffic or collect anyone’s personal data.
  • Use synthetic notes only. Never store real passwords, tokens, or client data in practice files.
  • If you’re unsure whether something is in scope, stop and ask a volunteer first.
